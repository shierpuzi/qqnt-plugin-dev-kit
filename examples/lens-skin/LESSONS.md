# LESSONS —— Lens 透镜踩坑复盘

README 记的是"实测值"，这里记的是**过程**：症状 → 当初的误判 → 根因 → 正解。
每条都发生过，不是假想。

环境：QQ NT 9.9.33-52230 + LiteLoaderQQNT 5.2.1 + Chromium 144 + Windows，2026-10-16/17。
本文件最初随插件 **v0.4.0（旧版）** 写下；第 1~18 条在 v0.9.1 上重验仍然成立，第 19~24 条是 v0.5→v0.9.1 期间（GPU 光源 / 玻璃面板 / 调试工具）新增的复盘。

## 1. 改完基色，界面出现两套蓝

- **症状**：把 `--brand_standard` 改成 Lens 的 accent，一部分蓝色变了，另一部分纹丝不动。
- **误判**："这些地方硬编码了颜色"或"我的样式被 QQ 覆盖了"。
- **根因**：QQ 的 `--nt_*` 派生令牌是**构建期预计算的字面色值**，不是从 `--brand_standard` 运行时推导的。改基色它们不会跟着变。实测 25 个蓝色系令牌仍是旧值。
- **正解**：用 `color-mix(in srgb, var(--lg-accent) N%, transparent)` 从唯一真源把**全部**派生令牌重新表达一遍。32/32 补齐后扫描 637 个元素 0 处旧色残留。

> 教训：**别假设一个令牌系统的基色是"活"的。** 先用探针把改动前后每个相关令牌的实际计算值 dump 出来对比。

## 2. "开关点不动"

- **症状**：设置页开关点下去，状态确实切换了（读配置是对的），但外观永远显示为关。
- **误判**："点击事件没绑上" / "QQ 的样式把我的 class 覆盖了"。
- **根因**：QQ 的 `.q-switch` 外观由 class **`is-active`** 驱动，**不是 `aria-checked`**。只改 `aria-checked` 时，无障碍语义对了，视觉一点没动。
- **正解**：切换时 `classList.toggle("is-active", on)`；`aria-checked` 照旧同步。开启态实测轨道 `rgb(40,117,237)`、手柄 `translate 12px`。

> 教训：**先问"这个控件的外观是谁驱动的"**，别按语义化 HTML 的直觉猜。QQ 的组件类名是内部实现，`role`/`aria-*` 只保证语义不代表视觉。

## 3. "设置改了要重启 QQ 才生效"（最像玄学的一个）

- **症状**：在设置页改开关/音量，主界面毫无反应；重启 QQ 后生效。但去翻 `config.json`，**磁盘上的值一直是对的**。
- **误判**：以为是 `LiteLoader.api.config` 写入有延迟、要等落盘 —— 于是去折腾 await 和防抖，全无效果。
- **根因**：QQ 每个窗口是**独立 JS 上下文**（主界面 `webcontentsid=2`、设置页 `webcontentsid=6`）。设置页里 `window.dispatchEvent(...)` **跨不过窗口**，主界面的声音层根本收不到。
- **正解**：`localStorage` 的 **`storage` 事件**（浏览器原生跨窗口机制，实测在 QQ 里可用）。两个补充：
  - `storage` **不在写入者自己的窗口触发** → 本窗口要另走一条 `CustomEvent`，两个通道缺一不可；
  - 载荷带 `_t: Date.now()`，否则连续两次相同配置不触发事件。
  - 实测：主窗口写入后，其它 **3 个窗口**都收到了通知。
- **顺带**：广播放在 `saveConfig()` 内部，而不是每个调用点，这样开关 / 滑杆 / 恢复默认三处都不会漏。

> 教训：**"写盘对了但没生效"要立刻怀疑进程/上下文边界**，而不是写盘本身。QQ 的多窗口是一个多进程世界，不是一份全局状态。

## 4. 音量滑杆"没反应"

- **症状**：拖音量滑杆，数值变了，声音一点不变；重启后才按新音量出声。
- **误判**：以为配置没传过去（其实传过去了）。
- **根因**：`master.gain.value` 只在 `AudioContext` 创建时设过一次。之后 `sound.volume = x` 只改字段值，**不碰音频图**。
- **正解**：给 `volume` 写 getter/setter，setter 里同步 `master.gain.value`。注意 setter 在 `master` 存在前要无副作用，所以初始化时用 `_volume` 而不是 `volume`。

> 教训：**"配置对象更新了"≠"运行时对象更新了"。** 有副作用的字段就要用 setter 把副作用绑上去，别指望调用点记得手动同步。

## 5. 滚动到边界时摩擦音一直在响

- **症状**：列表滚到底了，声音还在响，像永远没到边界。
- **误判**：几何公式写错了（于是去调容差、调精度）。
- **根因**：QQ 的消息列表是**虚拟列表**：实测 `scrollHeight` 是伪造的 **300000**，`clientHeight` 只有 **322**。`scrollHeight - clientHeight - scrollTop ≈ 0` **永远不成立**。另外 QQ 滚动容器的 `overflowY` 是 **`overlay`**，不是 `auto`/`scroll`。
- **正解**：换成**行为判据** —— 滚轮触发了但 `scrollTop` 没变化（同方向、变化 < 0.5px）→ 已在边界。对虚拟列表、普通列表、顶/底两个方向都成立；反向滚动时方向改变会正常恢复出声。

> 教训：**DOM 的几何属性可以被框架伪造。** 面对虚拟列表/虚拟滚动，用"行为有没有发生"判断状态，比用"几何应该等于多少"稳得多。

## 6. 原生拖动窗口：以为进程被冻住了

- **症状**：拖 QQ 顶栏时，`pointerdown`/`move`/`up` **一个都收不到**（全为 0）。
- **误判**："拖动期间 renderer 被阻塞了，所以做不了拖拽音效。"
- **根因**：`app-region: drag` 区域由**操作系统**处理，输入事件不走 JS；但渲染进程**完全正常**。实测：12 秒 **239** 次心跳、最长卡顿 **0ms**、窗口确实位移 **214px**。
- **正解**：轮询 `window.screenX/screenY` 反推窗口移动速度（90ms 一轮，位移 > 4px 视为拖动开始）。只对 `visibilityState === "visible"` 生效，后台窗口的 screen 值不可信。

> 教训：**"收不到事件" ≠ "这个进程死了"。** 换个可观测量（心跳、窗口坐标）再下结论。

## 7. 全站 `button` 规则让界面卡死

- **症状**：点左上角头像开资料卡时，界面直接卡死。
- **根因**：一条覆盖**全站 `button`** 的动效规则。QQ 里 `button` 用得极广，资料卡打开时大量匹配元素同时参与过渡计算。
- **正解**：动效选择器一律限定到具体的静态容器/组件。发送按钮那条甚至要精确到 `.chat-input-area .send-btn-wrap`。
- **注意**：这和下面第 8 条的 v1 冻结是**两次不同的卡死**，别混为一谈 —— 本条是选择器广度问题，第 8 条是观察器/动画问题。

> 教训：**在大型应用里写 CSS 规则，选择器广度就是风险本身。** 加规则前先数一下它会匹配多少个元素。

## 8. v1 让主窗口渲染冻结（嫌疑与规避）

- **症状**：动效层早期版本让 QQ 主窗口渲染冻结。
- **嫌疑**（源码里记的是"主要嫌疑"，未单独隔离验证）：
  1. 诊断用的**全文档 MutationObserver**，对每个新增节点递归 `getComputedStyle`；
  2. 给 **QQ 动态浮层**加 `animation` 且 `fill-mode: both`。
- **正解（v2 的三条铁律）**：
  1. 只作用于**始终存在的静态元素**（导航项/联系人项/按钮），**绝不**出现 `.q-popup` / `.q-dialog` / `.q-context-menu` / `.q-toast` 等动态浮层类名；
  2. 只用 CSS `transition` + 状态伪类（`:active`/`:hover`），**零 `@keyframes`、零 `animation`、零 `fill-mode`**；
  3. **不引入任何 JS 观察器**。

> 教训：**给宿主应用的动态浮层加特效，等于给自己埋雷。** 别用全文档观察器做诊断——它本身就是性能问题。

## 9. 用 `transform` 简写破坏了 QQ 自己的定位

- **症状**：动效层改 `transform: scale(...)` 之后，某些 QQ 元素位置跑偏。
- **根因**：`transform` 简写会**覆盖**元素既有的 transform，而 QQ 的弹窗可能正是用 transform 做居中定位。
- **正解**：用 `scale` / `translate` **独立属性**，与既有 transform **叠加而非覆盖**。

> 教训：**改别人的 CSS 时，属性越"独立"越安全。** 简写 = 全量覆盖，独立属性 = 局部叠加。

## 10. 发送按钮的弹性加错了元素

- **症状**：给发送按钮加 `:active` 缩放，只有文字在缩，蓝色块不动。
- **根因**：发送按钮**不是 `<button>`**，是 div 组合：最外层 `.send-btn-wrap` 才画蓝色背景（`rgb(40,117,237)`、**94×32**），内层 `.send`/`.send-msg` 只有文字与图标（60×32 / 28×28，背景透明）。
- **正解**：弹性加在 `.send-btn-wrap` 上。

> 教训：**"看起来是一个按钮"的东西，DOM 上可能是三层。** 先量一量哪个元素真的有背景。

## 11. 单击联系人会叠一层音

- **症状**：点一下联系人，出了两种音。
- **根因**：`pointerdown` 就开始起摩擦音，随后的 `click` 再播 `select`。
- **正解**：按下只记录起点，**位移超过 6px** 才真正开始摩擦音。

> 教训：**`pointerdown` 语义是"可能拖拽"，不是"拖拽"。** 用位移阈值区分意图。

## 12. 回车发送没声音

- **症状**：点发送按钮有声，按回车发送无声。
- **根因**：**回车不产生 `click`**。
- **正解**：另监听编辑器（`.qq-msg-editor, .ProseMirror, .ck-content`）上的 `keydown`，只认 Enter，排除 `isComposing`（输入法组合中）与 Shift/Ctrl/Alt/Meta（换行或组合键）。

> 教训：**"所有提交都走 click"是个错误假设。** 键盘路径要单独挂。

## 13. 悬浮音在快速划动时爆音 / 回到同一控件不再响

- **症状 A**：鼠标快速划过一整排按钮，变成密集爆音。
- **症状 B**：从控件移出再回到同一个控件，不响了。
- **根因 A**：悬浮音没有冷却，事件密度就是鼠标频率。
- **根因 B**：`pointerenter` **不冒泡**，只能用 `pointerover` + 记录上一个元素来模拟；但如果移到空白处时不清空记录，回来后判定"还是同一个元素"直接 return。
- **正解**：`grab` 冷却 **95ms**（70ms 过密、140ms 迟钝，95ms 是实测折中）；移出所有控件时把记录清空。

> 教训：**用"上一个元素"模拟 enter/leave 时，空白区域也是一次状态转移。**

## 14. 拖动滑杆不即时生效 / 写盘太频繁

- **症状**：拖音量滑杆，松手才有反应（或者干脆没反应）。
- **根因**：`onChange(saveConfig(patch))` 没 `await` → 传出去的是 **Promise**，声音层 `Object.assign(cfg, Promise)` 是个**空操作**。反过来，如果每次都立刻写，拖动时 `input` 高频触发会连续写磁盘。
- **正解**：`onChange(await saveConfig(patch))` + **160ms 防抖**（源码确认），停手后才落盘。

> 教训：**异步 API 忘 `await`，失败方式是"静默空操作"**，不会报错，最难查。

## 15. `eval.txt` 在每个窗口都执行

- **症状**：用调试插件的 `eval.txt` 热替换时，读回的探针值有时互相矛盾。
- **根因**：`eval.txt` **在每个窗口都执行**，所以改状态的脚本会**并发跑 N 次**，各窗口写回的值互相覆盖。
- **正解**：意识到"读回值"来自 N 个窗口的竞争结果，探针脚本要**带窗口标识**、或者只做只读探测。

> 教训：**调试工具本身有并发语义。** 用之前先确认它在几个上下文里跑。

## 16. 路径：`local:///绝对路径` 早期被误判为不可用

- **症状**：一开始认为只有 `local://profile/<相对路径>` 能读插件资源。
- **实情**：`local://profile/<相对路径>` 可读；`local:///绝对路径` **也可用**（早期误判为不可用）。但两者是**两个不同的模块实例**，各自维护状态。
- **正解**：仍推荐从 `LiteLoader.plugins[slug].path.plugin` 反推相对 `LiteLoader.path.profile` 的路径，**避免硬编码盘符**；用 eval 通道做探针时，操作页面**自己的**实例，不要自己 `import`（那会拿到另一份状态，还会多建一层覆盖层）。

> 教训：**"当时怎么试都不行"要保留成"当时不可用"，而不是升级成"原理上不可用"。**

## 17. 设置页改值忘了回写控件

- **症状**：点"恢复默认"，配置确实重置了，但滑杆和开关还停在旧位置 —— 看起来像"按钮没生效"。
- **根因**：只改了数据，没同步 UI。
- **正解**：`syncUI(next)` 统一回写开关的 `is-active` + `aria-checked`、滑杆的 `value` 与数值文本。

> 教训：**数据正确 ≠ 用户看到正确。** UI 是另一个状态副本，改数据要顺手刷它。

## 18. 配置里的 `null` 变成 0 导致静音

- **症状**：音量莫名变成 0（静音）。
- **根因**：`null` / `""` 被 `Number()` **静默转成 0**。
- **正解**：`clamp()` 里先显式挡掉 `null`/`undefined`/`""` 再用 fallback；`Number.isFinite` 不成立也走 fallback。

> 教训：**`Number()` 的隐式转换会吞掉"值不存在"和"值是 0"的区别。** 数值边界处必须显式判空。

## 19. 主界面凭空多出一个巨型光框：虚拟列表的隐藏测量副本（本轮最有价值的一条）

- **症状**：GPU 光源上线后，主界面联系人列表里**凭空多出一个和真实行等高的巨型圆角光框**，位置固定、跟着列表头滚不动（实测那个框是 **1029×72 @ (56,92)**，而真实行是 **304×72 @ (64,100)**）。
- **误判**（按顺序猜了三轮，全错）：
  1. "是 SDF 尺寸算错了" → 去查 `r.width/2 + MARGIN`（那是**另一个**已修过的 bug，见第 20 条的同类）；
  2. "是虚拟列表里某个占位容器太大" → 去调 `MAX_TARGET`（2000）和 `MAX_QUADS`（300），毫无作用；
  3. "是这个元素圆角取错了" → 去查逐元素 `borderTopLeftRadius` 的夹取。
- **根因**：QQ 的虚拟列表（`.viewport-list`）在 **`.viewport-list__measure`** 里放了一份**测量副本**：它用 `visibility: hidden` 隐藏（**仍占位**，`getBoundingClientRect()` **非零**、宽高都是真实值），却带着**同一个 `.recent-contact-item` 类**，宽度还是**整行宽**（1029，因为测量容器不受行内边距约束）。

  关键在于它**躲过了 rebuild() 里已有的每一道守卫**：

  | 守卫 | 为什么拦不住它 |
  |---|---|
  | 最小尺寸 `width < 10 \|\| height < 10` | 它 1029×72，远大于阈值 |
  | 尺寸上限 `MAX_TARGET = 2000` | 1029 < 2000，**永远命中不了上限** |
  | `Number.isFinite(...)` 的 NaN 检查 | 它的 left/top/width/height 都是正常有限值 |
  | 视口外过滤 `r.bottom < -200 \|\| r.top > innerHeight+200` | 它就在视口内（(56,92)） |
  | 数量兜底 `MAX_QUADS = 300` | 它排不到这么后 |
  | 圆角/尺寸逐元素读 | 反而更"正确"地画出了那个框 |

  **教训是：过滤条件的集合是"我以为的坏情况"，测量副本是"我没想到的坏情况"。** `getBoundingClientRect()` 非零**不等于**元素可见。
- **正解**：**复用 `rebuild()` 里紧接着就要取的 `getComputedStyle`**（下一行本来就要读 `borderTopLeftRadius`，所以这行守卫**零额外布局成本**）：

  ```js
  const cs = getComputedStyle(el);
  if (cs.visibility === "hidden") continue;      // ← 一行守卫
  const corner = parseFloat(cs.borderTopLeftRadius) || 0;
  ```

  顺序很重要：**先过可见性，再读圆角**，两者共用同一次 `getComputedStyle`。
- **只读元素自己的 `visibility`**：父级隐藏而自身 `visibility: visible` 的元素确实可见（这是 CSS 语义）；`display: none` 的矩形本来就是 0，已被最小尺寸挡掉，所以**不需要**额外查 `display`。
- **排查手法（只读探针，写进 `eval.txt`）**：

  ```js
  (() => {
    const rows = [...document.querySelectorAll(".recent-contact-item")].map(e => {
      const r = e.getBoundingClientRect(), cs = getComputedStyle(e);
      return { w: Math.round(r.width), h: Math.round(r.height), left: Math.round(r.left),
               vis: cs.visibility, parent: e.parentElement && e.parentElement.className };
    });
    return rows.filter(o => o.w > 400 || o.vis === "hidden");   // 明显宽于同行 + visibility:hidden 的那个就是它
  })()
  ```

  判据：**宽度明显大于同级真实行、且 `visibility: hidden`、且父级类名含 `measure`** 的那个就是测量副本。

> 教训：**"几何非零"只是"有盒子"，不是"看得见"。** 虚拟列表保证 DOM 里存在一批**不成对可见**的影子节点；凡是按几何筛选节点的地方，都要再过一道可见性——而最省的做法是把它并进你本来就要做的那次样式读取里。

## 20. 暗色主题下整套皮肤失效：选择器写死了 `light`

- **症状**：用户把 QQ 切到暗色主题，皮肤**整套不生效**（颜色、圆角、玻璃全没了），像插件没装。
- **误判**："暗色主题下 QQ 换了一套组件类名，我的选择器全失效了。"
- **根因**：QQ 的主题令牌挂在 `body` 上，**浅色是 `q-theme-tokens-light`，暗色是 `q-theme-tokens-dark`**。早期所有规则都写成 `body.q-theme-tokens-light ...`，暗色下没有一条能匹配上 —— **规则没失效，是压根没匹配**。
- **正解**：全部改成 `body:is(.q-theme-tokens-light, .q-theme-tokens-dark) ...`（`:is()` 的优先级取列表里最高的那个，行为可预期）。这是一个**机械替换**，但漏掉任何一条都会在暗色下留下一个"半透明窟窿"。
- **验收**：在**两种主题下各跑一遍**同一条探针，比较 `getComputedStyle(el)` 的 `--lg-*` 实际值；只在浅色下测等于没测。
- **后续纪律**：**新增任何 CSS 规则都要沿用 `:is(...)` 写法。** 只写 `light` 就会复发。

> 教训：**"样式没生效"先分清是"被覆盖"还是"没匹配"。** 后者看的是选择器能不能命中（`querySelectorAll(sel).length`），前者才看优先级。

## 21. 联系人行圆角"露角"：原生行背景 `.item__content` 没有圆角

- **症状**：给联系人行 `.recent-contact-item` 加了 14px 圆角和玻璃底，选中/置顶的那一行**四个角露出方角**，看起来像圆角外面又贴了一块方布。
- **误判**："是 `overflow: hidden` 没生效" / "是 GPU 光框画歪了"。
- **根因**：QQ 原生的行背景**不在父元素上**，而在子元素 **`.recent-contact-item--top .item__content`**：它用 QQ 自己的令牌 `--overlay_top`（实测 `#ffffff0f`）上色，而且**自己 `border-radius: 0`**。父元素变圆了，子元素的方角背景仍然铺满整行，于是四个角"露"出来。
- **正解**：**父元素改圆角时，把子元素的圆角一并改掉**：

  ```css
  body:is(.q-theme-tokens-light, .q-theme-tokens-dark) .recent-contact-item .item__content {
    border-radius: var(--lg-chrome) !important;
  }
  ```

  （用后代选择器一次覆盖，别等发现哪一行露角才逐条补。）
- **另一个选择**：把 `.item__content` 的背景直接设成透明，但那是**覆盖 QQ 原生样式**，要单独确认视觉副作用（置顶/选中态的区分会消失）。当前做法保留了原生底色、只收边。
- **风险**：这条依赖 QQ 的类名结构，QQ 改了行背景的类名或结构就会失效（表现为方角再次露出）。用调试工具（`dsh-debug-logger` 的元素选择器）点上去能直接看到它当前的实际 `border-radius`。

> 教训：**宿主应用里的"一块颜色"经常不在你以为的那个元素上。** 加圆角/裁剪前，先用元素选择器确认**到底是谁在画这块底**，然后父子一起收边。

## 22. 依赖 `requestAnimationFrame`，光影"粘"在旧位置

- **症状**：鼠标快速移动后光影停在旧位置，要等下次移动才跟上；轨迹检测里"事件已收到、`closest` 已命中、rAF 已调度"，但**回调从未执行**（同一轮测试里另一处自递归 rAF 却能跑 31 帧）。
- **误判**："是坐标算错了 / 节流太激进。"
- **根因**：QQ 里 **rAF 回调可能被丢弃**。更糟的是"节流窗口内丢掉中间坐标" —— 如果只保留"够 16ms 就画、不够就丢"，那么最后那一次 `pointermove` 的坐标永远写不进去。
- **正解**：**时间节流 + 定时器补写**，并且把待写坐标留住：

  ```js
  if (now - lastWrite >= WRITE_MS) { lastWrite = now; draw(); }
  else if (!pending) { pending = setTimeout(() => { pending = 0; draw(); }, WRITE_MS); }
  ```

- **顺带**：`document.hidden` 时直接 `return` 跳过绘制（省 GPU）；但这意味着最小化时 `readPixels` 全 0 —— **这是预期行为，不是 bug**（也曾因此困惑过一轮）。

> 教训：**不要把关键帧交给一个"可能不触发"的调度器。** 用能给出确定时间的 `setTimeout`，并保证最后一次输入不会被节流吞掉。

## 23. `blur(0px)` 仍然是全额合成开销

- **症状**：把"高斯模糊"滑杆拉到 0，视觉上确实不模糊了，但面板的合成成本一点没降；早期甚至以为"模糊 0 = 关闭"。
- **根因**：`backdrop-filter: blur(0px)` **仍然会让浏览器为元素建立 backdrop root**，合成成本照付，而视觉效果为零。
- **正解**：模糊为 0 时把**整条** `backdrop-filter` 置为 `none`（由 JS 写 `--lg-backdrop`），而不是只改半径：

  ```js
  target.style.setProperty("--lg-backdrop", blur > 0 ? `blur(${blur}px) saturate(1.5)` : "none");
  ```

> 教训：**"参数为 0"和"关闭"在很多 CSS 属性上不是一回事。** 想省成本就要真的把属性去掉，而不是把它调成 0。

## 24. "面板透明度"想管到整个界面 → QQ 卡死两次，最终整段回退

- **症状**：把透明度滑杆拉到 0，只有我们自己声明的那几层玻璃变透了，界面主体（消息面板、会话列表内层、侧栏）**仍然不透** —— 因为 QQ 自己在这些元素上刷了半透明白底（`.message-panel` / `.viewport-list__inner` / `.sidebar-nav`，透明度 0.5 / 0.2 …），它们不引用我们的变量。
- **第一反应**：把这些表层统一改写成 `var(--lg-glass)`，于是滑杆就能一路管到全透明（像素堆叠探针实测 `allBlockersTransparent: true`，"成功"了）。
- **根因（卡死的代价）**：**QQ 主界面失去响应，强制结束进程才能恢复，发生两次。** 把 QQ 自己的大面板改成半透明后，叠加 ①我们面板的 `backdrop-filter` 与 ②覆盖全窗口的 WebGL 光源画布，会让合成器持续走**"与桌面合成"的慢路径**。第一次改的是窗口根容器 `.global-container`，收窄到面板层后**仍然卡死**。
- **正解（刻意的取舍）**：**整段回退。** "面板透明度"只作用于我们自己声明的那几层玻璃 —— 表现是"玻璃层变透"，**不是**"整个界面变透"。透明度这点收益不值得让 QQ 卡死。
- **留下的条件**：若将来仍要做"整界面透明"，必须先去掉上面两项成本中的至少一项，并且**一次只放开一层**：

  1. 面板的 `backdrop-filter`（模糊为 0 时已经是 `none`）
  2. 全窗口 WebGL 光源画布

> 教训：**"像素级上做到了"不等于"系统级扛得住"。** 把宿主应用的大面积元素改成半透明，等于把整个合成路径拖到最慢的一条上；相邻的合成成本（模糊、全屏画布）会**相乘**而不是相加。做这类改动要能一次一层地回退。

## 一句话总纲

这次开发里**所有的坑，本质都是"假设了一个不成立的前提"**：

| 假设 | 实际 |
|---|---|
| 令牌基色是活的 | 派生令牌是构建期字面值 |
| `aria-checked` 驱动外观 | `is-active` 驱动 |
| 事件能跨窗口 | 每个窗口独立 JS 上下文 |
| 改字段就是改生效 | 有副作用的字段要 setter 同步 |
| 几何能判断滚动边界 | 虚拟列表的 `scrollHeight` 是假的 |
| 收不到事件就是进程死了 | 原生拖动只是不走 JS |
| 选择器越通用越省事 | 全站 `button` 规则会让界面卡死 |
| 数据对了就生效了 | UI 是另一份状态副本 |
| **矩形非零就是可见** | **虚拟列表的测量副本 `visibility:hidden` 但矩形正常** |
| **只写 light 主题就够** | **暗色走 `q-theme-tokens-dark`，整套规则不匹配** |
| **父元素圆角了子元素就圆了** | **原生 `.item__content` 方角会露出来** |
| **rAF 一定会回调** | **QQ 里会丢帧，要用定时器补写** |
| **把参数调成 0 就是关闭** | **`blur(0px)` 仍建 backdrop root** |
| **像素上做到了就等于能上** | **把 QQ 大面板改成半透明 → 合成器走慢路径 → 卡死两次，整段回退** |

**遇到"改了没反应"，先问"我假设了什么"，再去查代码。**
